# Деплой k711 (production)

Прод: **www.klimashkina711.ru**. Один сервер, один nginx: он отдаёт и headless **MODX**
(CMS, API квартир), и Next.js-фронтенд. Этот документ — про **фронтенд**. Бэкенд
(MODX) через этот пайплайн не выкладывается — см. раздел в конце.

> Хост, пользователь и ключи в репозиторий намеренно не вынесены: они лежат в
> настройках GitHub Actions (secrets/variables) и у владельца проекта.
> Ниже `<user>@<host>` — прод-пользователь и адрес сервера.

## Коротко

| Что нужно | Как |
|---|---|
| Выкатить `main` | влить PR в `main` (при включённой автовыкладке) или **Actions → Deploy production → Run workflow → deploy** |
| Откатить | **Run workflow → rollback** (поле `release` пустое — на релиз, бывший на проде до текущего) |
| Узнать, что на проде | **Run workflow → status** или `ssh <user>@<host> '~/k711-deploy/bin/deploy.sh status'` |

Выкладывать можно **только коммиты из `main`**. Пайплайн **выключен**, пока в репозитории
не задана переменная `DEPLOY_ENABLED=true` (см. «Первичная настройка»).

## Как это устроено

```
~/k711-deploy/
  bin/deploy.sh              ← установленный движок выкладки
  repo.git/                  ← bare-репозиторий, shallow-fetch из GitHub
  github_known_hosts         ← сверенный host key github.com (только он)
  releases/
    20260914-153012-53f2f63/ ← каждый коммит — отдельный каталог
  live.log                   ← история релизов, реально прошедших проверку на проде
  deploys.log                ← все попытки: время, действие, релиз, коммит, результат
  logs/<релиз>.log           ← полный лог npm ci + next build
  logs/job-*.out             ← полный вывод каждой выкладки/отката
~/app-new  →  ~/k711-deploy/releases/<текущий>     (симлинк; это cwd процесса pm2)
```

`deploy.sh deploy <main|SHA>`:

1. **Предпроверки:** pm2 запускает приложение из `~/app-new` (см. «Если pm2 пересоздавали»),
   свободно ≥ 2,5 ГБ, MODX отвечает (без него `next build` не пройдёт), никто не выкладывает
   параллельно.
2. **Код:** shallow-fetch `main` из GitHub. Если передан SHA — он обязан входить в `main`
   и **не быть старше** коммита, который сейчас на проде (для возврата назад есть `rollback`).
3. **Сборка в новом каталоге:** `git archive` → `npm ci --include=dev` → `next build`.
   Сборка идёт **не** в каталоге, который обслуживает трафик, поэтому работающий сервер
   не может подсунуть ей устаревший пререндер из `.next/cache` (ловушка сборки «на месте»,
   из-за которой главная выходила старой).
4. **Проверка сборки:** есть `BUILD_ID`, главная пререндерилась, у неё непустой `<title>`,
   в `<head>` есть все строки из [`deploy/head-markers.txt`](deploy/head-markers.txt)
   (счётчик AdRiver, подтверждение Google Search Console).
5. **Переключение:** `pm2 stop` → атомарная замена симлинка → `pm2 start`.
6. **Проверка здоровья:** в течение 90 с HTML главной должен содержать `BUILD_ID` **новой**
   сборки — трафик обслуживает именно она.
7. **Автооткат:** если проверка не прошла — прод возвращается на предыдущий релиз, неудачный
   удаляется, выкладка помечается упавшей.
8. **Уборка:** хранятся текущий и последние живые релизы (всего 3); недособранные остатки
   удаляются; у нетекущих удаляется `.next/cache`.

Если что-то падает **до** шага 5, прод не трогается вообще.

**Обрыв SSH не страшен.** `deploy` и `rollback` выполняются в процессе, отвязанном от
SSH-сессии, а сессия только показывает лог. Если соединение оборвалось или job в CI
отменили, выкладка всё равно доходит до конца или откатывается сама. Полный вывод — в
`~/k711-deploy/logs/job-*.out`, итог — в `deploys.log` и `status`.

**Откат** возвращает релиз, который **был на проде** до текущего (по `live.log`), а не
соседний по имени. Откатиться можно только на релиз, который хоть раз прошёл проверку на
проде. Если между «увидел проблему» и «нажал rollback» прошла ещё одна выкладка, указывайте
релиз явно (поле `release`, имя берётся из `status`).

## Модель доверия — прочитать до включения

- `deploy` **исполняет код из репозитория** под пользователем приложения: `npm ci`
  (lifecycle-скрипты зависимостей), `next build` (`next.config.ts`) и сам сайт. У этого
  пользователя на сервере есть sudo.
- Ключ CI в `authorized_keys` ограничен forced command: **сам ключ** не даёт shell. Но он
  выкладывает коммиты из `main`, а коммит может выполнить на сервере что угодно.
- На бесплатном тарифе у приватного репозитория нет защиты веток и защиты окружений, а
  секреты репозитория доступны workflow из любой ветки. Поэтому **любой с write-доступом к
  репозиторию после установки ключа CI может выполнить код на проде**. `DEPLOY_ENABLED` —
  защита от случайной выкладки, а не граница безопасности.
- Сейчас это не новый риск: подрядчикам уже передан SSH-ключ этого пользователя. Но ставить
  ключ CI стоит только осознанно.

Что реально сужает доверие (не сделано, требует решения): отозвать у подрядчиков личный
SSH-ключ; собирать под отдельным пользователем без sudo; выкладывать только коммиты,
подписанные владельцем (`git verify-commit` на сервере); либо тариф с защитой веток и
обязательным ревью окружения.

## Первичная настройка (один раз)

### 1. Сервер

Скопировать `deploy/deploy.sh` и `deploy/install.sh` в один каталог на сервере и запустить
под пользователем приложения (не root):

```bash
bash install.sh --ci-pubkey-file k711-github-actions-deploy.pub
```

Скрипт идемпотентен и **не перезапускает** приложение. Он:
- ставит `deploy.sh` в `~/k711-deploy/bin/`;
- создаёт ключ сервер→GitHub, получает host key github.com, **сверяет с официальным
  отпечатком** и закрепляет только его;
- один раз превращает боевой каталог `~/app-new` в релиз `…-legacy`, ставит на его место
  симлинк и заносит legacy в историю живых (на него можно откатиться);
- проверяет, что pm2 запускает приложение из `~/app-new`;
- добавляет ключ CI **ровно одной строкой** с `restrict,command="…/deploy.sh --ssh"`; если
  этот ключ уже есть в `authorized_keys` без ограничения — останавливается с ошибкой.

Обновить движок выкладки — запустить `install.sh` ещё раз с новым `deploy.sh` рядом.

> ⚠️ В чистый релиз попадает **только то, что есть в git**. На проде в `public/` лежат
> 72 файла вне репозитория (старые `.png` до перехода на webp). На 14.09.2026 проверено:
> ни код, ни MODX, ни страницы на них не ссылаются — первая выкладка их просто не перенесёт.
> Если что-то положено на сервер руками — сначала закоммитьте.

### 2. GitHub → Settings репозитория

- **Deploy keys → Add deploy key:** публичный ключ, который напечатал `install.sh`.
  «Allow write access» **не отмечать**.
- **Secrets and variables → Actions → Secrets:**
  - `DEPLOY_SSH_KEY` — приватная часть ключа CI;
  - `DEPLOY_KNOWN_HOSTS` — строка `known_hosts` сервера, сверенная с его отпечатком.
- **Variables:** `DEPLOY_HOST`, `DEPLOY_USER`.
- **Variables:** `DEPLOY_ENABLED` = `true` — только когда готовы. Действует и на push в `main`,
  и на ручной запуск.

## Повседневное

- **Автоматически:** push в `main` → проверка типов в CI → выкладка на сервере.
- **Устаревшие прогоны пропускаются:** «Re-run jobs» у старого прогона не выкатит старый
  коммит поверх нового — workflow выкладывает только текущую вершину `main`.
- **Очередь:** `deploy` и `rollback` идут строго по одному, начатую выкладку не отменяют.
  Ждать может только один прогон — новый вытесняет ждущий. `status` в очередь не встаёт.
- **Вручную по SSH** ключом CI:

  ```bash
  ssh -i <ключ-CI> <user>@<host> deploy main
  ssh -i <ключ-CI> <user>@<host> rollback
  ssh -i <ключ-CI> <user>@<host> rollback 20260914-153012-53f2f63
  ssh -i <ключ-CI> <user>@<host> status
  ```

  С обычным ключом — то же через `~/k711-deploy/bin/deploy.sh <команда>`.

## Если выкладка упала

Этап — в выводе и в `~/k711-deploy/deploys.log`, полный лог сборки — в `logs/<релиз>.log`.

| Результат | Что случилось | Прод |
|---|---|---|
| `fail:подготовка` | pm2 не из симлинка / нет места / MODX не отвечает / идёт другая выкладка | не тронут |
| `fail:получение кода` | нет доступа к GitHub, SHA не из `main` или старше текущего | не тронут |
| `fail:npm ci`, `fail:сборка` | ошибка зависимостей или `next build` | не тронут |
| `fail:проверка сборки` | нет `<title>` или строки из `head-markers.txt` | не тронут |
| `fail:health→откат` | новая сборка не ответила — выполнен автооткат | предыдущий релиз |
| `fail:health+откат-не-прошёл` | не поднялась ни новая, ни предыдущая сборка | **ручной разбор:** `pm2 logs k711` |

### Если pm2 пересоздавали

`deploy.sh` требует, чтобы pm2 запускал приложение из **пути симлинка**. pm2 запоминает
реальный путь текущего каталога, поэтому `cd ~/app-new && pm2 start …` «запечёт» конкретный
релиз, и переключение перестанет работать (`deploy.sh` откажет с понятной ошибкой).
Пересоздавать так:

```bash
export PM2_HOME=~/.pm2-node22
pm2 delete k711
PORT=3001 HOSTNAME=127.0.0.1 NODE_ENV=production \
  pm2 start npm --name k711 --cwd "$HOME/app-new" -- start
pm2 save
```

## Сервер: что ещё важно знать

- **pm2:** отдельный демон `PM2_HOME=~/.pm2-node22`, процесс `k711` (`npm start`).
  `.env` на проде нет: `API_BASE_URL` по умолчанию указывает на прод-MODX.
- **nginx** (`/etc/nginx/sites-available/default`): `location /` → `127.0.0.1:3001`;
  `= /api/lead` и `= /api/revalidate` — роуты Next; `/api/flats|flat|floor`, `/manager`,
  `*.php`, `/assets/` — MODX.
- **Node:** `deploy.sh` берёт Node 22 из `~/.nvm/versions/node` напрямую. Неинтерактивный
  `ssh … 'bash -lc …'` по умолчанию даёт системный Node 18 — собирать вручную так нельзя.
- **Старое приложение** `~/app` (Next 15) до сих пор работает на `:3000` под системным pm2
  (`~/.pm2`). Трогать его только системным pm2, никогда — node22-pm2.
- **SSH** иногда обрывает новые подключения, если их много подряд (fail2ban и ufw не
  установлены, похоже на ограничение провайдера) — повторите через минуту.

## Ограничения

- **Простой при переключении:** stop → start занимает несколько секунд, nginx отдаёт 502.
- **Холодный кэш картинок:** кэш оптимизатора изображений (`.next/cache/images`) у каждого
  релиза свой — после выкладки и отката картинки заново оптимизируются при первых запросах.
- **Version skew:** у пользователей с открытой вкладкой после выкладки старые JS-чанки
  пропадают. Next 16 решает это настройкой
  [`deploymentId`](https://nextjs.org/docs/app/api-reference/config/next-config-js/deploymentId)
  — пока не включена.

## Бэкенд (MODX)

Код MODX **не деплоится** этим пайплайном и в git на сервере не лежит: webroot `~/modx`
(владелец `www-data`), сниппеты, шаблоны и TV хранятся **в БД**.
- **Контент** — через админку `/manager`. После правки значений напрямую в БД нужна очистка
  кэша MODX (`core/cache`).
- **Данные квартир** — cron раз в сутки дёргает `/api/crm`.
- **Изменения кода** (setup-скрипты вида `_setup_*.php`) запускаются на сервере **от
  `www-data` из webroot**; перед запуском — свежий дамп БД. Если релиз меняет формат
  `/api/flats`, выкатывайте бэкенд и фронтенд одним окном.

## Формы / лиды

Лиды уходят в **CoMagic** из браузера (`src/lib/comagic.ts`, `sendLead()`); виджет CoMagic
подключается через **GTM**, а не из кода. `/api/lead` только логирует факт заявки и
резервным каналом не является. См. [KNOWN-ISSUES.md](KNOWN-ISSUES.md).
